## Разработка универсальной системы для ролевых игр живого действия (РИЖД / LARP)

### 1. Общая информация

Необходимо разработать программный комплекс для проведения ролевых игр живого действия (РИЖД / LARP).

Комплекс состоит из двух взаимосвязанных частей:

**1. Мастерская** — приложение для Windows, предназначенное для создания игровых проектов, наполнения их мультимедийными материалами, автоматической генерации цифровых кодов, экспорта данных для печати и формирования игровых сборок.

**2. Игрок** — мобильное приложение для Android и iOS, позволяющее игрокам вводить пятизначные коды и получать соответствующие текстовые и мультимедийные материалы.

Основное требование: мобильное приложение должно полноценно функционировать без доступа к интернету.

Система должна быть универсальной. Мастера должны иметь возможность создавать неограниченное количество разных игровых проектов, не изменяя программный код приложения.

**Текущая приоритетная задача — разработка мастерской для Windows.**

**Обмен данными:**

Технологии являются рекомендацией. Если существуют более надёжные варианты, предложить их с техническим обоснованием до изменения архитектуры.

### 3. Мастерская — Windows-приложение

Мастерская должна иметь полноценный графический интерфейс на русском языке.

Интерфейс должен быть понятным пользователю без навыков программирования.

Основные разделы:

1. Игровые проекты.
2. Записи и материалы.
3. Локации.
4. Список цифровых кодов.
5. Экспорт для печати.
6. Управление сборками и версиями.
7. Настройки приложения.

### 3.1. Управление проектами

Мастер должен иметь возможность:

- Создавать новый игровой проект.
- Указывать название и описание игры.
- Открывать существующий проект.
- Изменять параметры проекта.
- Сохранять проект на компьютере.
- Создавать копию проекта.
- Удалять проект после подтверждения.
- Продолжать работу с проектом после закрытия программы.

Каждый проект имеет собственную независимую базу записей и кодов.

Коды могут повторяться между разными проектами, но не внутри одного проекта.

### 3.2. Создание записей

Запись является основной единицей игрового контента.

Каждой записи соответствует ровно один уникальный пятизначный цифровой код.

Одна запись может включать неограниченное количество блоков содержимого.

Поддерживаемые типы:

- Текст.
- Изображения.
- Аудио.
- Видео.

В одной записи могут использоваться любые комбинации материалов, например:

- Текст + изображение.
- Видео + текст.
- Аудио + изображение.
- Несколько изображений + текст.
- Видео + аудио + изображения + текст.

Мастер должен самостоятельно управлять последовательностью блоков внутри записи.

Нужны функции:

- Добавить блок.
- Редактировать блок.
- Удалить блок.
- Изменить порядок блоков.
- Предварительно просмотреть запись так, как её увидит игрок.

Для текстового блока предусмотреть базовое форматирование: абзацы, заголовки, жирный и курсивный текст.

Для медиаблоков предусмотреть выбор файлов с компьютера.

Медиафайлы должны копироваться в хранилище проекта, а не оставаться зависимыми от первоначального пути на компьютере.

### 3.3. Генерация цифровых кодов

**Строгие требования:**

1. Каждый код состоит ровно из пяти цифр.
2. Генерация кода выполняется исключительно автоматически.
3. Ручное назначение и изменение кода запрещено.
4. Каждой записи соответствует один код.
5. Один код не может принадлежать двум записям внутри одного проекта.
6. После создания записи код закрепляется за ней.
7. Редактирование записи не меняет её код.
8. Обновление игровой сборки не меняет существующие коды.
9. Перед сохранением система проверяет уникальность.
10. Удалённые коды желательно резервировать в истории проекта, чтобы случайно не выдать их другой записи, если на игровом полигоне уже размещены печатные материалы.

По умолчанию использовать диапазон от 10000 до 99999, обеспечивающий 90 000 возможных комбинаций.

Генерация должна использовать надёжный генератор случайных чисел и проверку занятости кодов.

### 3.4. Локации

Необходимо реализовать справочник игровых локаций.

Примеры:

- Главный штаб.
- Лаборатория.
- Старый дом.
- Библиотека.
- Подземелье.

Мастер должен иметь возможность создавать, переименовывать и удалять локации.

Записи должны привязываться к локациям для последующей сортировки и распределения материалов по игровому полигону.

### 3.5. Таблица записей

В мастерской должна присутствовать таблица со следующими столбцами:

| Поле | Описание |
|---|---|
| Код | Автоматически сформированный пятизначный код |
| Название | Внутреннее название записи |
| Локация | Место размещения кода |
| Содержимое | Типы блоков: текст, фото, аудио, видео |
| Изменено | Дата последнего изменения |

Требуется поиск, фильтрация и сортировка записей.

Код должен быть доступен для копирования.

### 3.6. Экспорт кодов

Мастер должен иметь возможность выгружать список кодов для последующей печати и размещения на полигоне.

**Экспорт в Excel (.xlsx):**

- Все записи.
- Коды.
- Названия записей.
- Локации.
- Типы материалов.
- Возможность сортировки по локациям.

**Экспорт в PDF:**

- Карточки для печати.
- Крупный пятизначный код.
- Возможность группировки карточек по локациям.
- Удобное размещение нескольких карточек на листе A4.

Название записи и локацию выводить на карточке по настройке мастера, поскольку эта информация иногда может содержать сюжетные спойлеры.

### 4. Мобильное приложение игрока

Мобильное приложение должно быть максимально простым.

Главный экран:

- Поле ввода пятизначного кода.
- Цифровая клавиатура.
- Кнопка поиска / открытия.
- Отображение ошибок ввода.

После правильного ввода открывается соответствующая запись.

Приложение отображает её содержимое в установленном мастером порядке.

Все файлы должны открываться непосредственно внутри приложения.

**Повторный просмотр не ограничивается.** Игрок вправе открыть одну и ту же запись сколько угодно раз.

Не реализовывать механизмы однократного просмотра.

### 4.1. Защита от перебора кодов

Установлены следующие правила:

- После **3 неправильных попыток подряд** блокировать ввод кодов на **30 минут**.
- После правильного ввода сбрасывать счётчик неправильных попыток.
- Во время блокировки показывать оставшееся время.
- Блокировка должна сохраняться после закрытия приложения.
- Ранее открытые записи должны оставаться доступными для просмотра.

Счётчик и блокировку хранить локально.

Не требуется серверная авторизация игроков.

Понимать, что полностью защитить локальное состояние от очистки данных или переустановки без серверного контроля невозможно.

### 4.2. Автономность

После установки игровых материалов приложение должно работать без интернета.

Без сети должны функционировать:

- Ввод кода.
- Поиск записей.
- Отображение текста.
- Просмотр изображений.
- Воспроизведение аудио.
- Воспроизведение видео.
- Проверка неправильных попыток.
- Блокировка ввода.

Не использовать сторонние облачные проигрыватели и внешние ссылки для отображения игрового контента.

### 5. Игровые пакеты

Реализовать отдельный формат `.rpgpack`.

Файл представляет собой переносимый пакет проекта, содержащий:

- Идентификатор игры.
- Версию пакета.
- Список записей и кодов.
- Структуру блоков.
- Локации.
- Медиафайлы.
- Контрольные суммы файлов.
- Метаданные версии.

Пакет должен быть переносимым и не содержать абсолютных путей к файлам на компьютере мастера.

Предусмотреть импорт и проверку целостности.

Использовать атомарное обновление: новый пакет должен проверяться до замены предыдущей установленной версии. Ошибка импорта не должна повреждать действующую игру.

### 5.1. Ручное обновление без интернета

Мастер формирует обновлённый игровой пакет.

Файл передаётся игроку любым доступным способом.

Игрок открывает приложение, выбирает импорт обновления и указывает файл `.rpgpack`.

Приложение проверяет пакет и устанавливает новую версию базы материалов.

Переустановка мобильного приложения не требуется.

### 5.2. Онлайн-обновление

В перспективе должна поддерживаться публикация обновлений из мастерской через сервер.

Принцип:

1. Мастер изменяет игровой проект.
2. Создаёт новую версию.
3. Нажимает «Опубликовать обновление».
4. Сервер получает обновление.
5. Подключённые устройства узнают о новой версии.
6. Приложения загружают изменения.

Если интернет отсутствует, приложения продолжают работать с имеющимися материалами.

При восстановлении соединения обновление становится доступным.

Желательно реализовать дифференциальную загрузку: скачивать только изменившиеся файлы, а не всю медиатеку.

Серверный компонент не обязателен для первого рабочего прототипа, но архитектура мастерской и формата пакетов должна предусматривать дальнейшее подключение.

### 9. План разработки

### 10. Инструкция для Codex

Ты выступаешь в роли ведущего разработчика и архитектора программного комплекса.

Не ограничивайся концепциями, описаниями и макетами.

Требуется создавать реальные файлы исходного кода, рабочую структуру проекта, тесты и конфигурацию сборки.

Начни с **Этапа 1 — разработки Windows-мастерской**.

Принципы работы:

1. Сначала изучи существующий репозиторий и его структуру, если он уже создан.
2. Подготовь техническую архитектуру мастерской и структуру базы данных.
3. После этого приступай непосредственно к реализации.
4. Не используй временные заглушки вместо основного функционала без явной необходимости.
5. Не добавляй не согласованные с пользователем сложные функции.
6. Пиши модульный, сопровождаемый код.
7. Используй распространённые и поддерживаемые библиотеки.
8. Проверяй зависимости и версии библиотек.
9. Покрывай критическую бизнес-логику автоматическими тестами.
10. Проверяй результаты тестов и исправляй ошибки.
11. Предусмотри корректную обработку исключений.
12. При наличии инструментов сборки подготовь исполняемую Windows-версию.
13. Если сборка или GUI-тестирование недоступны в текущей среде, честно сообщи об ограничении.
14. После каждого этапа предоставляй краткий отчёт: что реализовано, какие тесты пройдены и что пока не проверено.
15. Сохраняй совместимость данных с будущим мобильным приложением.

**Главная цель:** разработать действительно работающую мастерскую, которой человек без навыков программирования сможет пользоваться для самостоятельного создания ролевых игр.

Начинай реализацию первого этапа прямо сейчас.
