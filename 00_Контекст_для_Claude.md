# Последние пожелания и статус реализации

# Последние требования и границы принятых решений

Этот файл передаёт смысл переписки; это не дословная выгрузка всей истории чата.
Раннее исходное ТЗ включено отдельно без изменений, текущие реализованные уточнения — SPEC.md.

Уже реализовано по сохранённому исходному коду версии 0.5.1:
1. Браузерная мастерская «Без правил», аккаунты и пароли; администратор видит всё,
   обычный мастер — свои и предоставленные ему проекты. Совместное редактирование.
2. Проектные группы видений («Сны», «ЭП» и т.д.) вместо локаций в интерфейсе.
   Старые ключи locations/location_id в формате сохранены для совместимости.
3. Текст, изображения, аудио, видео; стабильные коды; шаблон изображения,
   ручное размещение цифры и ZIP готовых к печати PNG; прежние PDF/Excel.
4. Android APK. Пока есть интернет, автоматически загружаются все активные проекты
   и игровые материалы. Предварительная отдельная публикация необязательна.
5. Игрок: выбор проекта → имя персонажа → числовой код → материал.
   Мастер видит список персонажей, первую/последнюю связь, без ложного статуса «онлайн».
6. Полный офлайн после загрузки; обновления материалов онлайн и файлом .rpgpack.
   Три ошибочных кода → блокировка 30 минут, переживающая перезапуск и обновление.
7. Вкладка «История» УБРАНА. Внутренние записи открытий и безопасности сохранены.
8. Видео 40 МБ: проценты/мегабайты, остановка передачи, сохранение черновика при
   ошибке, тайм-ауты, кеш. Автоматическое сжатие/перекодирование видео НЕ добавлено.
9. APK ARM64 около 22 МБ вместо универсального около 62 МБ; варианты подписаны
   одним ключом и устанавливаются поверх старого приложения. Медиа занимают место отдельно.
10. Постоянная страница скачивания без авторизации и QR на неё в PNG/SVG.

Новые потребности, обсуждаются, ещё НЕ реализованы:
- Игры примерно раз в полгода; пользователь не хочет круглогодичных расходов.
- Пользователь не программист, не знает английский; не хочет разбираться в сервисах
  и устанавливать Python/Node/набор инструментов. Нужна понятная русская программа.
- Предпочтительна Windows-мастерская с установщиком .exe, хранением игр на ноутбуке,
  редактированием без интернета и сохранением данных при обновлении приложения.
- Сохранить аккаунты/разделение прав, совместную работу и список персонажей при синхронизации.
- Ноутбук перемещается: дома SkyNet, на полигоне другая сеть, возможно мобильная.
  Доступ нужен через интернет из разных мест; фиксированный домашний IP не решает задачу.
- Сервер на ноутбуке допустим только пока ноутбук включён и подключён.
  Когда он выключен, ранее скачанные игры работают офлайн, новые данные недоступны.
- Предпочтение бесплатным решениям. CGNAT, исходящая скорость, число игроков,
  объём медиа, качество интернета и коммерческий статус мероприятия не установлены.
- Обсуждались временный VPS и бесплатный туннель Tailscale Funnel. Ни один вариант
  не выбран окончательно, не настроен и не проверен на игровой нагрузке.
- Возможность PWA-игрока для iPhone без Apple Developer обсуждалась, но такой игрок
  ещё не создан. Нужна отдельная проверка холодного старта офлайн и медиа на iPhone.

Текущее состояние: пользователь остановил реализацию архитектурных изменений,
хочет передать материалы Claude и получить независимую рекомендацию.
Не считать последнее предложение помощника утверждённой архитектурой.

Для каждого подхода объясни стоимость, условия бесплатности, смену IP/CGNAT,

# Карта базы

# Карта данных и правил

Это описание структуры, НЕ дамп реальных пользовательских данных.
Авторитетный исполняемый источник — SQL и код в 01_Source.

Облако: Supabase PostgreSQL + Auth + Storage. Проект utzlbksisgszuizwofjx.
Адрес и публичный ключ находятся в web/public/config.json и mobile/assets/config.json.
Авторизация: Supabase auth.users. Изначально согласованный администратор —
mgoutside16@gmail.com, только после подтверждения почты. Пароля в комплекте нет.

Основные таблицы public:
- workshop_projects: JSON-документ проекта, owner_id, revision, status, player_version.
- workshop_profiles: профиль аккаунта, email/display_name.
- workshop_admins, workshop_admin_bootstrap: административные права/первичное назначение.
- workshop_members: доступ коллег к проекту.
- workshop_invites: приглашения по email.
- workshop_deleted_projects: служебная авторизация очистки после удаления проекта.
- workshop_record_history: неизменная привязка идентификатора записи к коду.
- player_releases: опубликованные версии прежних .rpgpack, путь/размер/контрольная сумма.
- player_auto_sources: постоянная привязка идентичности игры к исходному проекту.
- player_participants: имена персонажей, связь с проектом, времена контакта и хеш токена устройства.
  Точное определение имени/полей см. player-auto-sync.sql; индекс SQL в schema-index.json.

Storage:
- workshop-media: медиа проектов и приватные шаблоны печати.
- player-releases: игровые архивы опубликованных версий.
Обычный SQL-дамп не является копией байтов файлов Storage.

Права:
- Администратор видит проекты всех мастеров; мастер — свои и общие проекты.
- Состав участников/приглашения управляются владельцем/администратором.
- Защита реализована в PostgreSQL/RLS/RPC, а не только скрытием кнопок.
- Все активные игровые материалы доступны игрокам автоматически по прежнему требованию.
  Это не модель «тайное содержимое защищено серверным кодом»: код ищется в скачанной игре.
- Финальная политика разрешает текущие публичные архивы и используемые игровой записью
  медиа. Метаданные и подписанные ссылки на эти же публичные файлы также могут быть доступны.
  Неиспользуемые файлы, шаблоны печати, проекты аккаунтов, участники и запись защищены.
- Не восстанавливать исторические ограничения по storage.operation/request.path вместо
  финальной политики: они вызывали реальный отказ скачивания.

Ключевые RPC:
- get_workshop_identity, list_workshop_users, set_workshop_display_name, set_workshop_admin;
- save_workshop_project, delete_workshop_project и управление участниками/приглашениями;
- get_player_catalog, get_player_snapshot, get_player_source_version;
- register_player, list_game_players;
- get_player_release, publish_player_release (совместимость прежней публикации).
Точный список функций/политик/таблиц со строками: schema-index.json.

Миграции для новой разработки читать в порядке:
schema.sql → account-update.sql → player-updates.sql → player-auto-sync.sql
→ player-public-downloads.sql (финальное правило, повторяемое).
Свежая player-auto-sync.sql уже содержит финальные политики.
first-admin.sql — отдельный вспомогательный путь назначения подтверждённого администратора.
invite-management.sql — историческое отдельное дополнение; функции есть в новой schema.sql.
player-download-access.sql — историческая попытка совместимости; не финальное правило.
Реальный порядок развёртывания/настроек Auth — README.md и backend/PLAYER-UPDATES.md.
test-bootstrap.sql создаёт заменители служебной схемы ТОЛЬКО для тестовой PostgreSQL;
он не заменяет работающие Supabase Auth и Storage и не выполняется в рабочей базе.

Локальные данные:
- Web IndexedDB — кеш по аккаунтам, не полноценная замена облачной базы.
- Android: SQLite player.sqlite + каталоги файлов versions. Схема v2 в PlayerStore.open.
- Старый desktop: проектная SQLite и папки медиа, см. docs/DESKTOP.md.
- .rpgpack: переносимый ZIP manifest.json + медиа и хеши. См. docs/RPGPACK.md.
  Пакет не заменяет резервную копию аккаунтов, прав и мастерских шаблонов печати.

Версии и совместная работа:
- revision применяется для конкурентного сохранения; изменения разных записей объединяются,
  конфликт одной записи оставляет черновик и требует решения пользователя.
- player_version монотонная; первая миграция резервирует номер выше прежних пакетов.
- идентичности игры/записи, коды, локальные блокировки не сбрасываются при обновлении.

# Ограничения экспорта облака

# Что есть в комплекте и что нужно выгрузить из облака отдельно

В комплект включены все отслеживаемые исходники, SQL-структура, функции, RLS,
триггеры, миграции, правила пакетов, оригиналы ТЗ/PDF, тесты и история main.
Но это НЕ полный бэкап Supabase: доступа к закрытым данным в этой сессии нет,
инструментов подключённого Supabase также нет. Публичный ключ такого доступа не даёт.
На последнем скриншоте владельца Supabase сообщает о паузе и сохранности данных.
Вероятная причина — низкая активность бесплатного проекта за 7 дней; точная причина
по аккаунтному журналу/уведомлению не проверялась.

Для полного переноса дополнительно нужны:
1. Настоящий экспорт PostgreSQL проекта, включая рабочие таблицы и связанные идентичности.
2. Байты объектов Storage обоих buckets, а не только метаданные storage.objects.
3. Конфигурация Auth: подтверждение почты, Site URL, разрешённые redirect URL и т.д.
4. Секреты/ключи — только через защищённый канал отдельно; не в контекст для Claude.

Простой путь сохранения игровых материалов владельцем после Resume project:
- войти в мастерскую;
- экспортировать каждый нужный проект в .rpgpack;
- отдельно сохранить печатные шаблоны и мастерские настройки, если они нужны;
- сохранить экспорт в нескольких местах.
Это сохранит игровые материалы, но не является полным переносом аккаунтов/прав.

В кабинете Supabase есть Download backups; проверьте доступные варианты экспорта
базы и файлов. Наличие и формат зависят от состояния проекта/тарифа. Нельзя обещать,
что одна кнопка выдаст все данные вместе со Storage. При необходимости разработчик
делает штатный экспорт после получения разрешённого доступа владельца.

Демонстрационные .rpgpack/SQLite/карточки из тестов в полном архиве НЕ являются
реальными текущими проектами аккаунта. Исторические тестовые логи тоже не бэкап.

Исходный прикреплённый текст и PDF найдены в рабочей папке и скопированы байт-в-байт.
Из логотипов включена сохранённая используемая версия; точные оригиналы всех трёх
вставленных в переписку изображений как отдельных файлов здесь не обнаружены.
Вся история переписки отдельным машинным экспортом не доступна; включена её
содержательная техническая сводка с явно отмеченными неопределённостями.

## Разработка универсальной системы для ролевых игр живого действия (РИЖД / LARP)

### 1. Общая информация

Необходимо разработать программный комплекс для проведения ролевых игр живого действия (РИЖД / LARP).

Комплекс состоит из двух взаимосвязанных частей:

**1. Мастерская** — приложение для Windows, предназначенное для создания игровых проектов, наполнения их мультимедийными материалами, автоматической генерации цифровых кодов, экспорта данных для печати и формирования игровых сборок.

**2. Игрок** — мобильное приложение для Android и iOS, позволяющее игрокам вводить пятизначные коды и получать соответствующие текстовые и мультимедийные материалы.

Основное требование: мобильное приложение должно полноценно функционировать без доступа к интернету.

Система должна быть универсальной. Мастера должны иметь возможность создавать неограниченное количество разных игровых проектов, не изменяя программный код приложения.

**Текущая приоритетная задача — разработка мастерской для Windows.**

---

### 2. Архитектура системы

Рекомендуемый технологический стек:

**Мастерская:**
- Python.
- PySide6 для графического интерфейса Windows.
- SQLite для локальной базы данных.
- SQLAlchemy для работы с данными.
- PyInstaller для формирования Windows-приложения.
- pytest для автоматизированного тестирования.

**Мобильное приложение:**
- Flutter.
- Android и iOS из единой кодовой базы.
- Локальная база SQLite.
- Встроенные средства отображения текста, изображений, аудио и видео.

**Обмен данными:**
- Универсальный формат игровых пакетов `.rpgpack`.
- Версионирование игровых проектов.
- Онлайн-обновления через сервер.
- Ручной импорт игровых пакетов без интернета.

Технологии являются рекомендацией. Если существуют более надёжные варианты, предложить их с техническим обоснованием до изменения архитектуры.

### 3. Мастерская — Windows-приложение

Мастерская должна иметь полноценный графический интерфейс на русском языке.

Интерфейс должен быть понятным пользователю без навыков программирования.

Основные разделы:

1. Игровые проекты.
2. Записи и материалы.
3. Локации.
4. Список цифровых кодов.
5. Экспорт для печати.
6. Управление сборками и версиями.
7. Настройки приложения.

### 3.1. Управление проектами

Мастер должен иметь возможность:

- Создавать новый игровой проект.
- Указывать название и описание игры.
- Открывать существующий проект.
- Изменять параметры проекта.
- Сохранять проект на компьютере.
- Создавать копию проекта.
- Удалять проект после подтверждения.
- Продолжать работу с проектом после закрытия программы.

Каждый проект имеет собственную независимую базу записей и кодов.

Коды могут повторяться между разными проектами, но не внутри одного проекта.

### 3.2. Создание записей

Запись является основной единицей игрового контента.

Каждой записи соответствует ровно один уникальный пятизначный цифровой код.

Одна запись может включать неограниченное количество блоков содержимого.

Поддерживаемые типы:

- Текст.
- Изображения.
- Аудио.
- Видео.

В одной записи могут использоваться любые комбинации материалов, например:

- Текст + изображение.
- Видео + текст.
- Аудио + изображение.
- Несколько изображений + текст.
- Видео + аудио + изображения + текст.

Мастер должен самостоятельно управлять последовательностью блоков внутри записи.

Нужны функции:

- Добавить блок.
- Редактировать блок.
- Удалить блок.
- Изменить порядок блоков.
- Предварительно просмотреть запись так, как её увидит игрок.

Для текстового блока предусмотреть базовое форматирование: абзацы, заголовки, жирный и курсивный текст.

Для медиаблоков предусмотреть выбор файлов с компьютера.

Медиафайлы должны копироваться в хранилище проекта, а не оставаться зависимыми от первоначального пути на компьютере.

### 3.3. Генерация цифровых кодов

**Строгие требования:**

1. Каждый код состоит ровно из пяти цифр.
2. Генерация кода выполняется исключительно автоматически.
3. Ручное назначение и изменение кода запрещено.
4. Каждой записи соответствует один код.
5. Один код не может принадлежать двум записям внутри одного проекта.
6. После создания записи код закрепляется за ней.
7. Редактирование записи не меняет её код.
8. Обновление игровой сборки не меняет существующие коды.
9. Перед сохранением система проверяет уникальность.
10. Удалённые коды желательно резервировать в истории проекта, чтобы случайно не выдать их другой записи, если на игровом полигоне уже размещены печатные материалы.

По умолчанию использовать диапазон от 10000 до 99999, обеспечивающий 90 000 возможных комбинаций.

Генерация должна использовать надёжный генератор случайных чисел и проверку занятости кодов.

### 3.4. Локации

Необходимо реализовать справочник игровых локаций.

Примеры:

- Главный штаб.
- Лаборатория.
- Старый дом.
- Библиотека.
- Подземелье.

Мастер должен иметь возможность создавать, переименовывать и удалять локации.

Записи должны привязываться к локациям для последующей сортировки и распределения материалов по игровому полигону.

### 3.5. Таблица записей

В мастерской должна присутствовать таблица со следующими столбцами:

| Поле | Описание |
|---|---|
| Код | Автоматически сформированный пятизначный код |
| Название | Внутреннее название записи |
| Локация | Место размещения кода |
| Содержимое | Типы блоков: текст, фото, аудио, видео |
| Изменено | Дата последнего изменения |

Требуется поиск, фильтрация и сортировка записей.

Код должен быть доступен для копирования.

### 3.6. Экспорт кодов

Мастер должен иметь возможность выгружать список кодов для последующей печати и размещения на полигоне.

**Экспорт в Excel (.xlsx):**

- Все записи.
- Коды.
- Названия записей.
- Локации.
- Типы материалов.
- Возможность сортировки по локациям.

**Экспорт в PDF:**

- Карточки для печати.
- Крупный пятизначный код.
- Возможность группировки карточек по локациям.
- Удобное размещение нескольких карточек на листе A4.

Название записи и локацию выводить на карточке по настройке мастера, поскольку эта информация иногда может содержать сюжетные спойлеры.

### 4. Мобильное приложение игрока

Мобильное приложение должно быть максимально простым.

Главный экран:

- Поле ввода пятизначного кода.
- Цифровая клавиатура.
- Кнопка поиска / открытия.
- Отображение ошибок ввода.

После правильного ввода открывается соответствующая запись.

Приложение отображает её содержимое в установленном мастером порядке.

Все файлы должны открываться непосредственно внутри приложения.

**Повторный просмотр не ограничивается.** Игрок вправе открыть одну и ту же запись сколько угодно раз.

Не реализовывать механизмы однократного просмотра.

### 4.1. Защита от перебора кодов

Установлены следующие правила:

- После **3 неправильных попыток подряд** блокировать ввод кодов на **30 минут**.
- После правильного ввода сбрасывать счётчик неправильных попыток.
- Во время блокировки показывать оставшееся время.
- Блокировка должна сохраняться после закрытия приложения.
- Ранее открытые записи должны оставаться доступными для просмотра.

Счётчик и блокировку хранить локально.

Не требуется серверная авторизация игроков.

Понимать, что полностью защитить локальное состояние от очистки данных или переустановки без серверного контроля невозможно.

### 4.2. Автономность

После установки игровых материалов приложение должно работать без интернета.

Без сети должны функционировать:

- Ввод кода.
- Поиск записей.
- Отображение текста.
- Просмотр изображений.
- Воспроизведение аудио.
- Воспроизведение видео.
- Проверка неправильных попыток.
- Блокировка ввода.

Не использовать сторонние облачные проигрыватели и внешние ссылки для отображения игрового контента.

### 5. Игровые пакеты

Реализовать отдельный формат `.rpgpack`.

Файл представляет собой переносимый пакет проекта, содержащий:

- Идентификатор игры.
- Версию пакета.
- Список записей и кодов.
- Структуру блоков.
- Локации.
- Медиафайлы.
- Контрольные суммы файлов.
- Метаданные версии.

Пакет должен быть переносимым и не содержать абсолютных путей к файлам на компьютере мастера.

Предусмотреть импорт и проверку целостности.

Использовать атомарное обновление: новый пакет должен проверяться до замены предыдущей установленной версии. Ошибка импорта не должна повреждать действующую игру.

### 5.1. Ручное обновление без интернета

Мастер формирует обновлённый игровой пакет.

Файл передаётся игроку любым доступным способом.

Игрок открывает приложение, выбирает импорт обновления и указывает файл `.rpgpack`.

Приложение проверяет пакет и устанавливает новую версию базы материалов.

Переустановка мобильного приложения не требуется.

### 5.2. Онлайн-обновление

В перспективе должна поддерживаться публикация обновлений из мастерской через сервер.

Принцип:

1. Мастер изменяет игровой проект.
2. Создаёт новую версию.
3. Нажимает «Опубликовать обновление».
4. Сервер получает обновление.
5. Подключённые устройства узнают о новой версии.
6. Приложения загружают изменения.

Если интернет отсутствует, приложения продолжают работать с имеющимися материалами.

При восстановлении соединения обновление становится доступным.

Желательно реализовать дифференциальную загрузку: скачивать только изменившиеся файлы, а не всю медиатеку.

Серверный компонент не обязателен для первого рабочего прототипа, но архитектура мастерской и формата пакетов должна предусматривать дальнейшее подключение.

### 10. Инструкция для Codex

Ты выступаешь в роли ведущего разработчика и архитектора программного комплекса.

Не ограничивайся концепциями, описаниями и макетами.

Требуется создавать реальные файлы исходного кода, рабочую структуру проекта, тесты и конфигурацию сборки.

Начни с **Этапа 1 — разработки Windows-мастерской**.

Принципы работы:

1. Сначала изучи существующий репозиторий и его структуру, если он уже создан.
2. Подготовь техническую архитектуру мастерской и структуру базы данных.
3. После этого приступай непосредственно к реализации.
4. Не используй временные заглушки вместо основного функционала без явной необходимости.
5. Не добавляй не согласованные с пользователем сложные функции.
6. Пиши модульный, сопровождаемый код.
7. Используй распространённые и поддерживаемые библиотеки.
8. Проверяй зависимости и версии библиотек.
9. Покрывай критическую бизнес-логику автоматическими тестами.
10. Проверяй результаты тестов и исправляй ошибки.
11. Предусмотри корректную обработку исключений.
12. При наличии инструментов сборки подготовь исполняемую Windows-версию.
13. Если сборка или GUI-тестирование недоступны в текущей среде, честно сообщи об ограничении.
14. После каждого этапа предоставляй краткий отчёт: что реализовано, какие тесты пройдены и что пока не проверено.
15. Сохраняй совместимость данных с будущим мобильным приложением.

**Главная цель:** разработать действительно работающую мастерскую, которой человек без навыков программирования сможет пользоваться для самостоятельного создания ролевых игр.

Начинай реализацию первого этапа прямо сейчас.

## Разработка универсальной системы для ролевых игр живого действия (РИЖД / LARP)

### 1. Общая информация

Необходимо разработать программный комплекс для проведения ролевых игр живого действия (РИЖД / LARP).

Комплекс состоит из двух взаимосвязанных частей:

**1. Мастерская** — приложение для Windows, предназначенное для создания игровых проектов, наполнения их мультимедийными материалами, автоматической генерации цифровых кодов, экспорта данных для печати и формирования игровых сборок.

**2. Игрок** — мобильное приложение для Android и iOS, позволяющее игрокам вводить пятизначные коды и получать соответствующие текстовые и мультимедийные материалы.

Основное требование: мобильное приложение должно полноценно функционировать без доступа к интернету.

Система должна быть универсальной. Мастера должны иметь возможность создавать неограниченное количество разных игровых проектов, не изменяя программный код приложения.

**Текущая приоритетная задача — разработка мастерской для Windows.**

### 3. Мастерская — Windows-приложение

Мастерская должна иметь полноценный графический интерфейс на русском языке.

Интерфейс должен быть понятным пользователю без навыков программирования.

Основные разделы:

1. Игровые проекты.
2. Записи и материалы.
3. Локации.
4. Список цифровых кодов.
5. Экспорт для печати.
6. Управление сборками и версиями.
7. Настройки приложения.

### 3.1. Управление проектами

Мастер должен иметь возможность:

- Создавать новый игровой проект.
- Указывать название и описание игры.
- Открывать существующий проект.
- Изменять параметры проекта.
- Сохранять проект на компьютере.
- Создавать копию проекта.
- Удалять проект после подтверждения.
- Продолжать работу с проектом после закрытия программы.

Каждый проект имеет собственную независимую базу записей и кодов.

Коды могут повторяться между разными проектами, но не внутри одного проекта.

### 3.2. Создание записей

Запись является основной единицей игрового контента.

Каждой записи соответствует ровно один уникальный пятизначный цифровой код.

Одна запись может включать неограниченное количество блоков содержимого.

Поддерживаемые типы:

- Текст.
- Изображения.
- Аудио.
- Видео.

В одной записи могут использоваться любые комбинации материалов, например:

- Текст + изображение.
- Видео + текст.
- Аудио + изображение.
- Несколько изображений + текст.
- Видео + аудио + изображения + текст.

Мастер должен самостоятельно управлять последовательностью блоков внутри записи.

Нужны функции:

- Добавить блок.
- Редактировать блок.
- Удалить блок.
- Изменить порядок блоков.
- Предварительно просмотреть запись так, как её увидит игрок.

Для текстового блока предусмотреть базовое форматирование: абзацы, заголовки, жирный и курсивный текст.

Для медиаблоков предусмотреть выбор файлов с компьютера.

Медиафайлы должны копироваться в хранилище проекта, а не оставаться зависимыми от первоначального пути на компьютере.

### 3.3. Генерация цифровых кодов

**Строгие требования:**

1. Каждый код состоит ровно из пяти цифр.
2. Генерация кода выполняется исключительно автоматически.
3. Ручное назначение и изменение кода запрещено.
4. Каждой записи соответствует один код.
5. Один код не может принадлежать двум записям внутри одного проекта.
6. После создания записи код закрепляется за ней.
7. Редактирование записи не меняет её код.
8. Обновление игровой сборки не меняет существующие коды.
9. Перед сохранением система проверяет уникальность.
10. Удалённые коды желательно резервировать в истории проекта, чтобы случайно не выдать их другой записи, если на игровом полигоне уже размещены печатные материалы.

По умолчанию использовать диапазон от 10000 до 99999, обеспечивающий 90 000 возможных комбинаций.

Генерация должна использовать надёжный генератор случайных чисел и проверку занятости кодов.

### 3.4. Локации

Необходимо реализовать справочник игровых локаций.

Примеры:

- Главный штаб.
- Лаборатория.
- Старый дом.
- Библиотека.
- Подземелье.

Мастер должен иметь возможность создавать, переименовывать и удалять локации.

Записи должны привязываться к локациям для последующей сортировки и распределения материалов по игровому полигону.

### 3.5. Таблица записей

В мастерской должна присутствовать таблица со следующими столбцами:

| Поле | Описание |
|---|---|
| Код | Автоматически сформированный пятизначный код |
| Название | Внутреннее название записи |
| Локация | Место размещения кода |
| Содержимое | Типы блоков: текст, фото, аудио, видео |
| Изменено | Дата последнего изменения |

Требуется поиск, фильтрация и сортировка записей.

Код должен быть доступен для копирования.

### 3.6. Экспорт кодов

Мастер должен иметь возможность выгружать список кодов для последующей печати и размещения на полигоне.

**Экспорт в Excel (.xlsx):**

- Все записи.
- Коды.
- Названия записей.
- Локации.
- Типы материалов.
- Возможность сортировки по локациям.

**Экспорт в PDF:**

- Карточки для печати.
- Крупный пятизначный код.
- Возможность группировки карточек по локациям.
- Удобное размещение нескольких карточек на листе A4.

Название записи и локацию выводить на карточке по настройке мастера, поскольку эта информация иногда может содержать сюжетные спойлеры.

### 4. Мобильное приложение игрока

Мобильное приложение должно быть максимально простым.

Главный экран:

- Поле ввода пятизначного кода.
- Цифровая клавиатура.
- Кнопка поиска / открытия.
- Отображение ошибок ввода.

После правильного ввода открывается соответствующая запись.

Приложение отображает её содержимое в установленном мастером порядке.

Все файлы должны открываться непосредственно внутри приложения.

**Повторный просмотр не ограничивается.** Игрок вправе открыть одну и ту же запись сколько угодно раз.

Не реализовывать механизмы однократного просмотра.

### 4.1. Защита от перебора кодов

Установлены следующие правила:

- После **3 неправильных попыток подряд** блокировать ввод кодов на **30 минут**.
- После правильного ввода сбрасывать счётчик неправильных попыток.
- Во время блокировки показывать оставшееся время.
- Блокировка должна сохраняться после закрытия приложения.
- Ранее открытые записи должны оставаться доступными для просмотра.

Счётчик и блокировку хранить локально.

Не требуется серверная авторизация игроков.

Понимать, что полностью защитить локальное состояние от очистки данных или переустановки без серверного контроля невозможно.

### 4.2. Автономность

После установки игровых материалов приложение должно работать без интернета.

Без сети должны функционировать:

- Ввод кода.
- Поиск записей.
- Отображение текста.
- Просмотр изображений.
- Воспроизведение аудио.
- Воспроизведение видео.
- Проверка неправильных попыток.
- Блокировка ввода.

Не использовать сторонние облачные проигрыватели и внешние ссылки для отображения игрового контента.

### 5. Игровые пакеты

Реализовать отдельный формат `.rpgpack`.

Файл представляет собой переносимый пакет проекта, содержащий:

- Идентификатор игры.
- Версию пакета.
- Список записей и кодов.
- Структуру блоков.
- Локации.
- Медиафайлы.
- Контрольные суммы файлов.
- Метаданные версии.

Пакет должен быть переносимым и не содержать абсолютных путей к файлам на компьютере мастера.

Предусмотреть импорт и проверку целостности.

Использовать атомарное обновление: новый пакет должен проверяться до замены предыдущей установленной версии. Ошибка импорта не должна повреждать действующую игру.

### 5.1. Ручное обновление без интернета

Мастер формирует обновлённый игровой пакет.

Файл передаётся игроку любым доступным способом.

Игрок открывает приложение, выбирает импорт обновления и указывает файл `.rpgpack`.

Приложение проверяет пакет и устанавливает новую версию базы материалов.

Переустановка мобильного приложения не требуется.

### 5.2. Онлайн-обновление

В перспективе должна поддерживаться публикация обновлений из мастерской через сервер.

Принцип:

1. Мастер изменяет игровой проект.
2. Создаёт новую версию.
3. Нажимает «Опубликовать обновление».
4. Сервер получает обновление.
5. Подключённые устройства узнают о новой версии.
6. Приложения загружают изменения.

Если интернет отсутствует, приложения продолжают работать с имеющимися материалами.

При восстановлении соединения обновление становится доступным.

Желательно реализовать дифференциальную загрузку: скачивать только изменившиеся файлы, а не всю медиатеку.

Серверный компонент не обязателен для первого рабочего прототипа, но архитектура мастерской и формата пакетов должна предусматривать дальнейшее подключение.

4. Уникальность кодов.
5. Сохранение неизменного кода при редактировании.
6. Создание записей с несколькими типами материалов.
7. Сохранение порядка блоков.
8. Копирование медиафайлов в хранилище.
9. Экспорт Excel.
10. Экспорт PDF.
11. Создание игрового пакета.
12. Проверка содержимого пакета.
13. Импорт игрового пакета.
14. Обновление записи без изменения кода.

## Вход и личный кабинет

Зарегистрируйте аккаунт с почтой и паролем и подтвердите почту по ссылке из письма.
Войдите на сайт. Сначала назначенный администратор — `mgoutside16@gmail.com`;
права назначаются только после настоящего подтверждения этой почты.

Администратор видит все проекты и раздел пользователей. Мастер видит свои
проекты и проекты, куда его добавили. Владелец или администратор добавляет коллегу
по почте в «Участниках проекта». Для ещё не зарегистрированного пользователя
сохраняется приглашение; его можно отменить. После регистрации и подтверждения
почты приглашённый получает доступ. Участники редактируют проект совместно.

второй редактор получает предупреждение, его несохранённый текст остаётся в окне.
Права проверяются RLS базы и серверными функциями, а не скрытием кнопок.

## Работа с играми

1. Создайте проект и группы видений — например «Сны» и «ЭП».
2. Создайте записи с текстом, фото, аудио и видео. Код выдаётся автоматически и
   сохраняется при изменениях. Используйте предпросмотр и порядок блоков.
3. В «Кодах и печати» загрузите изображение одной карточки или откройте готовый
   пример «Сновидение» из предоставленного PDF. Выберите группу, перетащите код,
   задайте размер, цвет и шрифт. Сохраните шаблон группы.
4. Скачайте ZIP: внутри отдельные PNG с кодами в исходном разрешении и 300 dpi.
   По одному шаблону можно выгрузить до 500 карточек; есть ограничение памяти.
   Также остаются выгрузки Excel и обычный PDF A4.
5. Создайте `.rpgpack` для игрока или резервной копии материалов. Оформление
   мастерских карточек хранится отдельно в облачном проекте аккаунта.

Проекты, медиа и шаблоны находятся в Supabase и доступны с других компьютеров.
IndexedDB — кеш, разделённый по аккаунтам; при выходе он очищается. Старое
локальное хранилище предыдущей версии не удаляется. Администратор может явно
перенести старые проекты в аккаунт через «Перенести прежние проекты»; исходные
копии сохраняются. Старые локации показываются как группы, коды не меняются.

Для облачного сохранения нужен интернет. Квоты и максимальный размер файлов
зависят от тарифа Supabase (на бесплатном тарифе обычно 50 МиБ на файл).

# Формат игровых пакетов

# Формат .rpgpack v1

ZIP UTF-8, `manifest.json` и плоский каталог `media/`. Нет абсолютных путей,
внешних ссылок и исполняемого содержимого. Отсутствие шифрования означает, что
пакет предназначен для автономного распространения, а не защиты от владельца устройства.

Manifest:

| Поле | Значение |
| --- | --- |
| format_version | 1 — версия схемы, неизвестные версии отклоняются |
| version | Целое число от 1, увеличивается при каждом экспорте |
| created | Время UTC ISO 8601 |
| game | id (UUID), name, description |
| locations | Список {id: положительное целое, name: строка} |
| records | Список {id: UUID, code: строка 10000–99999, title, location_id, modified, blocks} |
| reserved_codes | Все когда-либо выданные коды, включая удалённые |
| checksums | Словарь относительный media-путь → SHA-256 (hex lowercase) |

`location_id` — существующий id либо null. `blocks` — упорядоченный список
`{kind, value}`; kind: `text`, `image`, `audio`, `video`. Для текста value — HTML
с базовым форматированием; клиент обязан фильтровать активные элементы и внешние
ресурсы. Для медиа value — `media/<имя файла>`. Мастерская пишет имена по SHA-256
с исходным расширением. В пакете ровно те медиа, на которые ссылаются блоки.
Необязательное информационное поле `location` у записи содержит имя локации;
источник связи — `location_id` и справочник locations.

Импорт проверяет схему, UUID, коды и связи, имена файлов, дубли, запрет симлинков,
размеры и SHA-256. Имена, совпадающие без учёта регистра, и несовместимые с Windows
имена (устройства, ADS, завершающие точки/пробелы) отклоняются. Числовые id и
версия ограничены диапазоном SQLite INTEGER (1–9223372036854775807).
Затем создаёт временную соседнюю папку, восстанавливает SQLite
транзакцией и переименовывает папку в новую целевую. Рабочий проект не заменяется.
Ограничения v1: ZIP ≤4 ГиБ распакованных данных, файл ≤1 ГиБ, manifest ≤16 МиБ,
не более 100 000 архивных файлов. Это защитные ограничения, не квоты на блоки
при редактировании проекта. Для очень больших игр понадобится потоковый формат.

При перезаписи пакета предыдущий файл хранится во временной соседней резервной
копии до фиксации транзакции версии. Обрабатываемая ошибка возвращает старый
файл и откатывает историю базы. Если процесс принудительно прерван или отключено
питание, рядом может остаться `.имя.rpgpack.larp-recovery-*`: это предыдущий
пакет для ручного восстановления. Автоматическое восстановление после сбоя питания
между фиксацией базы и публикацией файла в v1 не гарантируется.

Будущий игрок читает manifest и медиа без Python и SQLite мастерской. Установка
обновления на мобильном устройстве должна сначала проверить новый пакет,
сопоставить UUID и версии, затем атомарно переключить активную версию. Состояние
попыток и истории просмотра следует хранить отдельно от обновляемого пакета.
Мобильная установка/обновление и дифференциальная загрузка ещё не реализованы.

# Архитектура аккаунтов

# Аккаунты, группы и шаблоны карточек — 25.10.2026

Пользователь остановил Android до написания мобильного кода. Текущий приоритет —
веб-мастерская «Без правил». Требования: вход по логину/паролю, разные аккаунты
с независимыми проектами, доступ к ним с разных компьютеров; фирменный знак на
боковой панели; группы видений вместо локаций; изображения карточек с кодами,
которые размещаются вручную на загруженном шаблоне.

## Решения

Уточнение: полноценный личный кабинет и совместная работа. Глобальные роли:
администратор (все проекты/аккаунты) и мастер (свои и предоставленные проекты).
Владелец проекта и администратор управляют участниками. Любой участник-редактор
может работать с записями. При одновременной правке разных записей изменения
объединяются через повтор операции на актуальной версии; для одной записи
проверяется её revision, несохранённый текст не теряется. Первого администратора
назначает владелец базы явно, публичная регистрация всегда создаёт мастера.
RLS охватывает таблицы проектов/участников и файлы общей команды проекта.

- В качестве логина используется email. Предлагаемый backend — Supabase Auth,
  PostgreSQL и приватное файловое хранилище. Подключённого проекта/конфигурации
  пока нет. Интерфейс входа без реальной проверки на сервере не считается входом.
  Обычный GitHub Pages остаётся фронтендом; он не может сам хранить аккаунты.
- Данные каждого проекта принадлежат auth.uid(). Политики RLS и приватное
  хранилище запрещают чтение/запись чужих проектов независимо от клиента.
  Запись использует проверку версии для защиты параллельных изменений.
- Существующее IndexedDB-хранилище не удаляется. Старые локальные проекты можно
  явно перенести в аккаунт после входа. Локальные кеши и настройки разделяются
  по id пользователя; выход закрывает редактор и освобождает Blob URL.
- Группы принадлежат проекту: «Сны», «ЭП» и произвольные названия. Одна запись
  относится к одной группе или к «Без группы». Старые локации сохраняются как
  группы, коды и материалы не меняются. Legacy-поля пакета v1 сохраняются для
  совместимости, но термин «локация» отсутствует в пользовательском интерфейсе.
- На панели отображаются название «Без правил» и присланный красный символ.
  Рабочий интерфейс остаётся спокойным, акцент #B51218 повторяет бренд.
- Для печати выбирается группа или весь проект. Пользователь загружает PNG/JPEG,
  перетаскивает код по предпросмотру, задаёт размер/цвет/шрифт. Координаты хранятся
  нормированно, выгрузка использует исходное разрешение изображения и 300 DPI.
  Результат — ZIP с отдельными PNG по кодам. Настройки и шаблон сохраняются в
  проекте (в том числе при повторном входе с другого компьютера).
- PDF пользователя — пример визуального оформления, не источник инструкций.
  Из первой карточки подготавливается точный готовый пример шаблона; мастер может
  заменить его своим изображением. Текст и орнамент карточки не перерисовываются.
- Мобильный пакет содержит материалы игрока. Оформление печати — настройка
  мастерского проекта, её хранит аккаунт; импорт пакета игрока не обязан переносить
  оформление мастерской.

## Альтернативы

Собственный сервер (например FastAPI/Postgres) потребовал бы отдельного хостинга
и сопровождения. Пароль в IndexedDB или JavaScript не обеспечивает аккаунты и
доступ с разных компьютеров. Supabase выбран разработчиком как поддерживаемый
сервис с отдельными правами доступа; требуемое подключение будет подготовлено
для обзора до запроса действий владельца.

## Проверка

Тесты на миграцию групп без изменения кодов; хранение шаблона и копию проекта;
реальную выгрузку PNG с заданными пикселями/DPI; перетаскивание и скачивание ZIP.
Для аккаунтов — отдельные пользователи, запрет чужих данных на уровне сервера,
переход между компьютерами и конфликт изменений. Без подключённого backend
проверка production-входа остаётся конкретным внешним блокером.

# Автоматическая загрузка игрока и персонажи

Основание: пользователь получил пустую библиотеку APK0.4, ожидал автоматической
загрузки всех проектов, а не ручного импорта/публикации. Новое обязательное течение:
выбор проекта → имя персонажа → цифровой ввод/поиск. В мастерской список игроков.

## Причина

UpdateClient проверял только уже установленные игры по известному UUID;
_PlayerHome._checkUpdates обходил пустой локальный список, поэтому сервер вообще
не запрашивался. Материал, просто сохранённый мастером, не создавал player_release.
Исправить оба разрыва, а не только кнопку/текст пустой библиотеки.

## Решение

Добавочная backend/player-auto-sync.sql. Все active-проекты автоматически доступны
игрокам через каталог и снимки игровых данных. Приватные таблицы мастерской,
профили/роли/печатные шаблоны не открываются. Игровые материалы и коды уже входят
в передаваемые игрокам .rpgpack; здесь пользователь явно запросил автоматический
доступ ко всем проектам. Ручная публикация не требуется. Каталог обновляется при
запуске, resume и раз в20сек в foreground. Скачивание и установка автоматические,
с понятным постоянным прогрессом/ошибками и сохранением офлайн-копий при сбое.
Ручной .rpgpack и старый ссылочный протокол сохраняются.

### Серверные интерфейсы

workshop_projects.player_version bigint — независимая монотонная версия игрового
содержимого. BEFORE-триггер на запись повышает её при изменении данных игрока;
игнорирует изменения одних печатных шаблонов/служебной истории. Начальное значение
не меньше document.version, revision и прежнего опубликованного номера. Если
мастер экспортирует .rpgpack, version = max(document.version+1, player_version+1),
при сохранении документа триггер поднимает player_version до той же версии.
Storage.playerVersion(id) локально возвращает game.version; CloudStorage запрашивает
get_player_source_version(p_project_id uuid), доступный своим/общим мастерам.

player_auto_sources привязывает gameUUID к исходному projectUUID. Сначала
привязываются прежние публикации, затем active-проекты в порядке создания.
Импорт той же gameUUID не перехватывает опубликованную игру; независимая копия
имеет новую gameUUID. Привязка сохраняется как tombstone после удаления проекта.

RPC get_player_catalog(p_after uuid default null,p_limit integer default100)
returns JSON array объектов {game_id,project_id,name,description,version,
record_count,updated_at}, сортировка game_id, limit≤200. Анонимный клиент листает
до конца, не ограничивает молча число проектов. Все active, включая пустые.

RPC get_player_snapshot(p_game_id uuid) -> null либо:
{game_id,project_id,version,manifest,files:[{path,storage_path,size,sha256}]}
manifest — обычный .rpgpackv1: format_version,version,created,game,locations,records
(без revision),reserved_codes,checksums. checksum для media/SHA256.ext извлекается
из имени; для старых обычных имён может быть null и вычисляется телефоном после
TLS-загрузки. files содержит только медиа записей, без печатных шаблонов.
storage_path = projectUUID/media/file. Доступ к чтению workshop-media анонимно
только GET текущих referenced-файлов привязанного active-проекта, без listing/
изменения/чтения неигровых файлов. Метаданные size и наличие всех файлов проверяются.

### Персонажи

RPC register_player(p_game_id uuid,p_character_name text,p_token text) ->
{participant_id,character_name,first_seen,last_seen}. Token — случайный секрет
32bytes на устройстве отдельно для каждой игры; сервер хранит SHA256, не оригинал.
Имя1..100символов, без управляющих. Upsert по(game_id,token_hash), изменение имени
не плодит дубликаты. Анонимный пользователь не может перечислить участников.
RPC list_game_players(p_project_id uuid) -> JSON array таких объектов;
только master can_access проекта/админ. Список показывает персонажа и последнюю
связь, не утверждает достоверный realtime-online статус офлайн-игрока.

PlayerStore SQLite schema2 добавляет profiles, не меняя games/security/history.
PlayerProfile(gameId,characterName,token,pending). Методы:
playerProfile(gameId) -> PlayerProfile?;
playerProfiles() -> List<PlayerProfile>;
savePlayerProfile(gameId,name) -> PlayerProfile (сохраняет существующий token);
markPlayerRegistered(gameId,token,name) -> void (снимает pending только при совпадении).
Имя/проект не сбрасывают блокировку или историю. Офлайн профиль сохраняется сразу,
регистрация отправляется при связи; heartbeat только выбранной игре, pending
отправляются по всем сохранённым профилям. Никакой авторизации/пароля игрока.

### Телефон

UpdateClient получает catalog/snapshot через HTTPS/publickey, identity encoding
(обход Android native wrapped-zlib bug). Снимок + неизменяемые медиа скачиваются
потоково во временную папку; повторно используются проверенные файлы установленной
версии по SHA. Для legacy filename без checksum загружается заново. Собирается
потоковый ZIP без сжатия и вызывается существующий guarded installPackage,
ожидаемый UUID/версия проверяются до atomicSQLite switch. Неверный снимок, потеря
сети, нехватка места сохраняют старую игру/историю/блокировку. Удаление серверного
проекта не удаляет его офлайн-копию автоматически.

API UpdateClient: catalog()->List<CatalogGame>, syncGame(CatalogGame,{onProgress})
->InstalledGame? (null уже актуален), registerProfile(PlayerProfile)->void.
CatalogGame(gameId,projectId,name,description,version,recordCount,updatedAt).
Существующие check/install для архивных публикаций остаются. UI владеет циклом
синхронизации и регистрацией, передаёт selected-profile heartbeat.

## Проверка

RED до реализации: пустой чистый телефон сам получает проект/материал без UUID,
файла и Publish; изменения мастера повышают syncversion и сами приходят;
ручной пакет после автосинхронизации тоже устанавливается; SQLitev1→v2 сохраняет
старые данные; имя/смена проекта не снимают lock; pending registration уходит при
восстановлении связи; мастер видит только игроков доступного проекта.
Настоящие PostgreSQL, SQLite, HTTP, Chromium и Android. После добавочной миграции
проверить РЕАЛЬНЫЙ пользовательский проект по publicAPI (без печати сна/спойлеров)
и реальную установку на Android, затем отключить сеть и снова открыть материал.
Новый APK ставится поверх0.4 тем же ключом (versionCode5), без удаления приложения.

## Уточнение после проверки настоящего Storage

Контекстные operation/method/path-проверки не сработали в размещённом Storage.
Финальные player SELECT политики проверяют только активную каноническую связь
медиа/текущую публикацию. Метаданные и подписанные ссылки этих уже публичных
игровых файлов доступны; print/unreferenced/staged, аккаунты и запись закрыты.
Это заменяет первоначальное внутреннее ограничение listing, не требовавшееся
пользователем, и не расширяет перечень доступных игровых материалов.
